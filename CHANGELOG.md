# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Native plug-in hosting merged into main, experimental and off by default: the driver plug-in host (`plugin_host=1`, `input_strips=1`) and the daemon's native insert transactions, chains, delay compensation and licence mirror. No plug-in mappings ship; a user-side bundle builder is in progress.

## [2.0.0] - 2026-10-19

The first release that ships no Universal Audio files. `bash scripts/setup.sh` reads what your
Apollo needs from a UAD install you already have (Windows on another partition or a boot disk, a
Windows VM, Wine, or a copied folder), builds the driver, and installs the native mixer console
with plug-in windows. The web console, the tray and the Nix packaging are gone. Running UAD
plug-ins on the Apollo's DSP is not in this release. See `docs/install.md`.

### Removed
- The Nix flake, the NixOS module and the `nix` CI job: one install path, `bash scripts/setup.sh`.
- The web console (`console-web/`) and the system tray indicator (`tools/open-apollo-tray.py`, its icons and autostart entry, and the AppIndicator dependency): the native console (console-rs, `uaconsole`) replaces both. The `open-apollo-console` launcher and its fallback to UA's Windows Console under Wine are gone too; the menu entry runs `uaconsole`. The uninstallers still remove what older installs left behind.

### Changed
- USB DSP init (`tools/usb-full-init.py`): the repository no longer carries `tools/usb-re/init-bulk-sequence.bin`, the Windows capture of a Solo USB's DSP bring-up, which held five of UA's DSP modules. The init builds the same 38 frames from the modules the setup wizard or `oa-assets firmware` extracts from your own UAD install (`/lib/firmware/universal-audio/dsp`, or `--dsp-dir DIR`; each must match its SHA-256, `--accept-unknown-modules` to try another version) and from `tools/uausb/solo-usb-init.json`, which keeps the rest of what the capture had: the strip parameter blocks, the frame sizes and first sequence number, the module ids and hashes and the captured stream's SHA-256, no UA code. At 48 kHz the frames are byte-identical to the capture, and the log says whether they are. `--replay` sends that stream with the old fixed timing, `--capture FILE` takes everything from a capture of your own, and `--check` verifies the modules without touching a device. `scripts/install-usb.sh` stops before changing anything when the modules are missing, points to the setup wizard or `oa-assets firmware` (not UA's download page) when the USB boot image or the modules are missing, installs the facts with the `uausb` package and no longer copies the capture (it deletes an earlier install's copy). `tools/usb-re/make-solo-init-facts.py` writes the facts from a capture. The tests use made-up modules of the same sizes and compare the stream with the capture outside the code by hash; when the extracted modules are installed, one test checks the whole stream against the capture's SHA-256. Untested on hardware.
- The committed device maps (`device_map_apollo_x4.json`, `device_map_apollo_x8p.json`) and Mixer Helper tree (`helper_tree.json`) are structure only. UA's plug-in catalogue, factory channel-strip and I/O-map preset menus and Mixer Helper help text are no longer shipped, and neither is the capture machines' data (an Apollo serial number, hardware ids, a session path, MIDI devices, LAN addresses, home paths, account feature flags, licence state). The x4 map has 7,944 controls (was 9,924).
- Mixer daemon: overlays the UA catalogue that `oa-assets import` writes from the user's own UAD install (`~/.local/share/open-apollo/ua-catalogue/`, `--ua-catalogue DIR`, `$OA_UA_CATALOGUE`; `--no-ua-catalogue` to skip): the `/plugins` list, the factory channel-strip presets on every input and aux, the factory I/O presets before the user's saved ones, and the helper help strings (matched by position and SHA-256 through `device_maps/helper_tree.pins.json`). Without an import the plug-in list and factory menus are empty; nothing else changes. `tests/test_shipped_data.py` keeps UA content and host data out of the shipped files.
- Console host commands (`console_presets`): the preset menus of channels, auxes, inserts and `/plugins` entries list the imported factory preset names (locked, after the user's own) when no `--factory-presets-dir` folder holds that plug-in's files; loading a name that has no file says so. Without an import they list the user's own presets only.
- Setup wizard (`open-apollo-setup`): one password prompt and always a clean reinstall. A new "Review and install" page shows the chosen UAD install, what an earlier open-apollo install left (`uninstall.sh --list`), a "Keep my current install" option (off by default) and the opt-in report box; one Install button runs `scripts/setup-root.sh` through pkexec, and the "Remove previous install", "Import assets", "DSP programs & firmware" and "Driver" pages follow its progress. Unmounted Windows partitions are opened read-only by that run (no separate udisks prompt); VM disk images are still attached by udisks as you and detached from the Done page. Afterwards the Console is built as you and the mixer daemon restarted so it sees the imported art. If the password dialog is cancelled or the UAD install can't be used, nothing is changed. `--demo` simulates the whole run.
- `scripts/uninstall.sh` removes every trace of an install: every `ua_apollo` DKMS version (it took only the first) and the modules they built for every kernel, system and per-user daemon drop-ins, the user's WirePlumber and PipeWire rules (it removed only the system ones), the Console (`install-uaconsole.sh --uninstall`), old tray and launcher files, and a USB install (`uninstall-usb.sh`, which now accepts `--yes`). It ends with a check that lists anything still there and exits 1 if a file is left. New flags: `-y/--yes` (ask nothing; nor without a terminal), `--purge` (also `/lib/firmware/universal-audio`, `/lib/firmware/ua_apollo`, `~/.local/share/open-apollo`, `~/.cache/open-apollo`, which a default run keeps) and `--list` (what is installed, no root). It finds the desktop user under pkexec too.
- Mixer daemon: the WebSocket API (port 4721, for UA Connect-style clients; the web console was its user) is off by default. Start it with `--ws` or `--ws-port N`; `--no-ws` is still accepted.

### Security
- Install report: no user name, host name, home path, machine id or serial numbers. PipeWire state is reduced to the Apollo's own objects (allowlisted properties) plus a count of other audio objects by class, instead of the first 500 lines of `pw-dump` with every client's user and host and the user's other devices; the Apollo serial in the driver log is redacted. The report is still sent only when you opt in.

### Added
- Driver plug-in host (experimental, ABI 1.8, everything off by default; see `HARDWARE-SESSIONS.md` and `mixer-engine/NATIVE-HOSTING.md`): per-DSP ownership (a DSP is used only after a cold start found it freshly powered), each DSP's pool ledger from its registers, request transactions that wait for the DSP with `ua->lock` released, a module catalog read by the driver itself from `/lib/firmware/universal-audio/`, uploads that wait for the DSP's acknowledgement, zero-fill and memspec, `/proc/asound/cardN/plugin_host`. `input_strips=1` builds the Console Mic Input Strips on DSP 0 through it (x4, after a power cycle). `plugin_host=1` adds `UA_IOCTL_BOARD_QUERY` (0x90: the device's own per-plug-in authorization table, fresh, unmodified) and `UA_IOCTL_PLUGIN_INSTANCE` (0x94), whose CREATE reads that answer first and places nothing unless the device admits the plug-in (authorized, or a demo running); instances belong to their open file. GET_PLUGIN_CAPS reports operations only while accepted. The mixer daemon mirrors the device's answer on `/plugins/N/{Authorized,Status,Demoing,DemoDaysRemaining}` when the driver has `plugin_host=1` (`plugin_license.py`, the Mac engine's status strings, unknown on any failure, never cached across a reconnect or rate change); `PluginStartDemo` fails with hardware (demos are started in UA's own software). Not yet on hardware.
- Status map: a plug-in mapping row (`docs/status/plugin-library.json`, exported from the library ledger with `tools/gen-status-graph.py --library`): one square per UA-built UAD-2 plug-in in scope, by stage (live on the Apollo, mapped offline, on hold, blocked, not authorized on the test Apollo), with a README badge.
- Support and install docs for the release: `SUPPORT.md` (what to check, what to attach, never UA files); `docs/uad-install.md` adds what setup takes from the install, Windows on a second drive or an external USB boot disk (Rufus Windows To Go), Fast Startup and Windows 11 device encryption, Windows 11 VMs (UEFI, TPM), VirtualBox/VMware disks, copying through a VM shared folder and what to do after a UAD update; `docs/install.md` has a Plug-ins section (panels yes, DSP processing not in this release) and the `oa-assets dsp` step; the bug report form asks where the UAD install came from and for `oa-assets status`. README: the `driver-v2` notes are gone (it is merged), plug-in windows are listed.
- `scripts/setup.sh`: one command to install. It checks for Rust 1.89+ and a C compiler, builds the setup wizard and `oa-assets`, and starts the wizard (`--demo` walks through it without changing anything). It refuses to run as root or without a desktop session.
- Documentation in the repository: `docs/install.md` (requirements, the wizard page by page, the command-line and USB installs, uninstalling, where every file goes, troubleshooting), `docs/uad-install.md` (getting the UAD install setup reads: dual boot, a Windows VM, a Wine prefix or a copied folder), and the index `docs/README.md`. The README leads with `bash scripts/setup.sh`; ARCHITECTURE.md shows the setup flow and the console crates.
- Plug-in panel specs: setup's import step installs the open-apollo-panels release pinned in `configs/plugin-panels.conf` (224 schema-2 specs, a 1 MB download) into `/usr/share/open-apollo/plugin-specs`, where uaconsole finds them, so plug-in windows draw their own panel once `oa-assets plugins` has made the art (206 of 224 panels from a UAD 12 install; the rest show the parameter list). `scripts/install-panels.sh` refuses a tarball whose SHA-256 differs from the pin, one with links, more than one top folder or unexpected files, and swaps the specs in with one rename; `--from`/`--sha256` install a panels build of your own (`setup-root.sh --panels`/`--panels-sha256`, or `$OA_PANELS_TARBALL`/`$OA_PANELS_SHA256` for the wizard). A failed download only warns. `uninstall.sh` removes the specs (kind `panels`). The repo guard refuses `PluginSpec_*.json` files in this repository. `cargo run -p plugin-ui --example availability` reports which panels can open and why the others can't. Tests: `tests/test-install-panels.sh`.
- `mixer-engine/device_maps/unison_plugin_ids.json`: the 47 plug-ins (by plug-in id, no names) that load in a Unison preamp slot. No UAD install file says which do, so the UA catalogue import cannot; the overlay now sets `/plugins/N/Unison` from this list when the import has no flag of its own. Console's Unison checks (`console_inserts`, software model) read that flag and refuse a plug-in the catalogue lists as not Unison or does not list; with nothing imported the daemon cannot tell and does not refuse.
- `scripts/setup-root.sh`: the setup wizard's one privileged run. It opens a Windows partition read-only if asked (`--mount`, ntfs3 or ntfs-3g), checks the UAD install with `oa-assets scan --json` and stops there, changing nothing, if the Console art or the DSP programs' sources are missing; then removes the earlier install (`uninstall.sh --yes --purge`, unless `--keep-current`), imports the art as the desktop user, extracts the firmware, installs the driver (`install.sh --yes`) and closes the partition again, printing `::step <id> start|done|warn|failed|skipped` markers. `oa-assets scan --json` reports `firmware_inputs`. Unit tests: `tests/test-uninstall.sh`, `tests/test-setup-root.sh` (stubs and a fake root only).
- Status map in the README (`docs/status/`, `tools/gen-status-graph.py`): one square per behaviour of UA's drivers in the parity map, per task of the work plan and per Apollo model, coloured verified on hardware / done in code / partial / still to figure out / understood, not done / plugin hosting / needs hardware, with per-area numbers and the open tasks in `docs/status/README.md`. CI checks it is up to date.
- `tools/extract-ua-dsp-modules.py`: copies UA Console's built-in input-strip DSP modules (Mic Input Strip 0EB/0DA/0A5/0C2/12B, Input Strip 0DB, Talkback 0C9) from the user's own UA install (Windows, Wine or macOS) to `/lib/firmware/ua_apollo/dsp/`, for the driver's input strips; nothing UA-made is shipped. Found all seven in the Windows install on titan.
- Mixer daemon: plugin-slot lifecycle, publication, transactions and remote readback modules (ported from the Codex Wine work, `plugin_*.py`). Inert unless a plugin backend is injected: without one, effect-slot SETs and GETs and saved state behave as before. No driver plugin operations exist yet (GET_PLUGIN_CAPS reports none).
- `tools/daemon-protocol-check.py`: checks a running mixer daemon's Console protocol (text/UBJS/JSON framing, split headers, oversize frames, clock SET refusals, the clock-source menu; `--write` for the gain companion and `/Dirty`, putting each setting back).
- `UA_IOCTL_GET_PLUGIN_CAPS` (0x07, ABI 1.3): a read-only report of the DSP state (firmware/rings/audio connected, ring mask, parked DMA buffers) that advertises zero plugin operations.
- Driver host tests (`driver/tests`, compiled C snippets and source checks) for the device lifetime, clock, DSP-send and payload-validation invariants, adapted from the parallel Codex work.
- `notif_irq` (experimental, default off): the notification interrupt starts the DSP service pass at once instead of waiting for the 10 ms poll (titan: 27 interrupt-driven passes over 7 rate changes, poll kept as the fallback). The probe logs a passive interrupt self-test (`irq_selftest`, writes nothing).
- Driver: `Line N HiZ Impedance` ALSA controls (2.2M to 21k) on the HiZ inputs; error counters (forced XRUN stops, PCIe errors, AX_CONTROL faults, DSP error vectors, block-send errors) in `/proc/asound/cardN/dsp_state` with a rate-limited `UA_EVT_DEVICE_ERROR` event; ABI 1.2: PCIe link speed/width, clock-source mask and firmware rate mask in `UA_IOCTL_GET_SYSTEM_INFO`; `SET_MIXER_PARAM` channel type 3 sends the rate acknowledgement from user space.
- Mixer daemon: SoloSafe and Isolate exempt a channel from another channel's solo (the x4's talkback input is Isolate); the `/ClockSource` list follows the sources the device offers; `/AudioStreaming` follows the transport; Undo/Redo and I/O-map preset commands; `/openapollo/pcie_link`. Generated maps carry the digital mirror and output pads only on models that have them.
- `setup-apollo-io.sh --output-delay NAME=FRAMES` delays an output by up to 255 frames with a PipeWire filter chain (output delay compensation; the driver maps the DMA ring directly, so it cannot delay in the kernel). `tools/usb-reg-probe.py` uses the Windows vendor-request map and only reads unless told otherwise; the USB init warns when the Apollo is not on a SuperSpeed link. README: network/firewall ports and dynamic debug.
- Mixer daemon: `post` object commands get the Mixer Engine's replies ("Unable to resolve the command for the post." / "Unable to execute command.") instead of silence, and the host-side ones work: Identify, ClearClips, ClearSolos, CopyChannel/PasteChannel/CopyToSends, snapshots, channel presets and sessions. Sessions, snapshots and presets are the daemon's own JSON files, not UA's XML.
- Mixer daemon: stops writing to the hardware while the driver reports the device paused for system suspend, and pushes the mixer state again on resume (the preamp and monitor values still come from the hardware).
- Mixer daemon: reports the unit's real serial number (from `UA_IOCTL_GET_SYSTEM_INFO`), checks the driver's feature bits before using the newer bus-param flags (an older driver would have written a pan's right weight into the left entry), and has `--stereo-sends` (right-hand send entries; off until a listening test). `tools/oa-daemon-client.py` sets, gets and watches daemon paths.
- The driver reports its known delay to ALSA (`runtime->delay`): the FRAME_CFG safety offset on playback (8/16/32 frames per rate band) and the x4's converter latency on capture (4-5 frames); `report_delay=0` turns it off. The WirePlumber rule adds matching `latency.internal` properties.
- The driver replays the cached bus coefficients after a DSP program load. A solo-mute flag on the bus-param ioctl (ABI 1.1) sends a soloed-out weight as the macOS Mixer Engine does, with `bus_solo_sign=1` (experimental; the feature bit is offered only then). `toslink_in_bit` (experimental) carries the TOSLink input type into the device-mode word.
- Driver interface: `UA_IOCTL_GET_VERSION` (ABI 1.0 plus feature bits; `-ENOTTY` means an older driver), `UA_IOCTL_GET_SYSTEM_INFO` (the real 16-character serial, types, mixer kind, rate/clock/lock, unit role), `UA_IOCTL_GET_PAUSE_INFO` with `UA_EVT_PAUSED`/`UA_EVT_RESUMED` events around rate changes, suspend and removal, and `UA_IOCTL_SET_MIXER_BUS_PARAMS` (up to 64 bus-param entries under one lock). Units register in a group with a master (the first unit); a lone unit behaves as before.
- Clock: a read-only `Clock Locked` control (`(0xC07C & 3) == 1`, as the macOS driver defines it) with a `UA_EVT_CLOCK_LOCK` event on each change, AX_CONTROL fault-flag counters (bits 7/8), a bus-read latency histogram, and `/proc/asound/cardN/clock` (rate, source menu from the device, firmware rate mask, latency words, FRAME_CTR after the arm, clock-ack bits).
- `/proc/asound/cardN/dsp_state` (each DSP's status window, pools, boot word, rings, bus-enable mask, coefficient cache) and `/proc/asound/cardN/period_irq`; `tools/apollo-report.sh` collects them.
- The driver caches every mixer bus coefficient (bus, param, side) and can replay the cache after a DSP restart (`ua_dsp_replay_bus_params`); bus coefficients go to the bus's owner DSP and DSP 0.
- Mixer params for the surround, HP-correction and trim families (other params 0x4d-0x52, 0x55-0x62, 0x65, 0x69, 0x6b-0x82, 0x88-0x8a), gated by mixer kind as the macOS driver does.
- Mixer daemon: reads the driver's event channel (rate, clock source, lock, connect, offline, layout) and only polls as a fallback with an older driver; re-applies the saved state the hardware cannot report back (sends, aux, CUE, outputs, talkback configuration) once per connection, in the Mixer Engine's order; attenuates the outputs for a moment while a new sample rate settles, as the Mixer Engine does on the x4 (OutputsAttenuate, other param 0x20; `--mute-on-rate-change`, default 1 s); maps HiZ impedance, stereo link, alt monitors, CR PGA bypass, outputs attenuate, jack sensing, talkback master, line-out pads and 24 dB mode to their mixer params; CUE 3/4 outputs and sends on 4-cue models.
- Experimental module parameters (all default off, runtime-writable where noted): `period_irq` (period wakeups from the hardware period timer through a threaded IRQ handler, with a watchdog that falls back to the hrtimer; see `tools/period-irq-test.sh`), `dsp_msg_irq` (DSP message FIFO and DSP vectors), the clock/transport A/B knobs `frame_ctr_gate`, `notif_kext_reads`, `adopt_fw_rate`, `rate_ack_real`, `clock_ack_bit5`, `frame_cfg_win`, `clock_src_from_device`, `stall_qos_us`, and `dma64_audio` (audio rings above 4 GiB). `satellite_msi` (default on) gives UAD-2 Satellite TB units MSI as the Windows driver does.
- Mixer daemon: the front panel's selection reaches clients as `SelectedOnFront` (the monitor or CUE 1 when the front panel is on an output, else the selected preamp input; readback word 0 bits 26/27 and word 3 [30:28], applied as the Mixer Engine does), and `AltMonSelection` (word 6 [29:28]), Link (`Stereo`), `AnalogBoardID` (word 33 [28:26]), `LowNoisePreamps` (word 2 bit 30) and `Temperature` (word 17 [15:8]) follow the hardware on maps that have those controls. Readback preamps 5-8 (words 5 and 7) are decoded on models with more than four preamps.
- Event channel: `read()`/`poll()`/SIGIO on `/dev/ua_apolloN` return `struct ua_event {code, arg, time_ns}` records (per-open queue of 64, oldest dropped and reported). Codes follow the macOS driver (0x64-0x68, 0x6e: rate, IO descriptor, clock source, notification status) plus Linux ones (device offline, connected, layout changed, events lost); see `ua_ioctl.h` and `tools/ua-events.py`.
- The macOS driver's public device type (UAD2DeviceType, x4 = 0x1A) is computed at probe, logged, returned in `UA_IOCTL_GET_DEVICE_INFO` (`public_type`) and shown in `/proc/asound/cardN/io_map`; the output-mute and mixer-kind decisions use it.
- `/proc/asound/cardN/mixer_state`: front-panel fields of the hardware readback (headphone focus, selected input, alt-monitor selection, low-noise preamps, temperature, analog board id).
- `UA_IOCTL_GET_MIXER_PARAM` channel type 0 returns the mask of enabled mixer buses.
- Experimental module parameters for an A/B against the macOS driver's start-up (all default off): `kext_connect` (ring connect plus dated finalize after the ACEFACE handshake, chosen by public type, the x4 included), `dma_per_dsp` (one DMA_CTRL enable bit per DSP, no reset strobes left set), `warm_transport0` (TRANSPORT = 0 on every start), `dsp_status_check=2` (fail probe on a DSP status fault; `1`, the default, logs each DSP's status word), `block_strict` (a DSP block error fails the send) and `sendblock_chunk` (2 or 4 KB DMA pieces).
- Model data: each `devices/*.json` lists its clock sources, and runtime-generated device maps carry per-model `/devices/0` capability flags (correction, bass management, autogain, Dante, alt monitors, spans) instead of the x4's. The daemon knows the Dante clock source.
- `dsp_ready_wait` module parameter (experimental, default 0): on a cold start, poll each DSP's ready word before setting up its rings and retry a failed DSP connect once, as the macOS driver does when `ext_caps[7:4] == 1` (`1` = that rule, `2` = every v2 device). The Apollo x4 reports 1, so macOS polls on it; the default stays off until a cold-start test.
- ALSA controls follow the front panel: monitor level, mute, mono, dim, talkback, both headphone volumes, and each preamp's switches, gain and HiZ detect update (with change events) when the hardware changes them. New controls: `Headphone 1 Playback Volume`, read-only `Headphone 2 Playback Volume` and `Line N HiZ Detect Switch`.
- Installer: the mixer daemon runs as a systemd user service (`ua-mixer-daemon.service`, restarted on failure) instead of a background process started once; `driver/dkms.conf` is tracked; old `io_map=`/`mixer_mailbox=` overrides in `/etc/modprobe.d` are reported.
- `configs/pipewire/setup-apollo-io.sh` builds its loopbacks from the driver's `/proc/asound/cardN/io_map` (same node names), with `--dry-run`, `--io-map FILE`, `--card N` and opt-in Virtual loopbacks (`--virtual`).
- `tools/apollo-report.sh` (read-only diagnostic report, no personal data) and `tools/apollo-selftest.sh` (opt-in duplex test per sample rate with PASS/SILENT/DEAD/ROUTE verdicts) for owners of other models; see `tools/TESTING.md`.
- `tools/check-models.py` checks `devices/*.json` against itself, the generated header and the driver's hand-written tables (run in CI).
- Mixer daemon: models without a captured device map get one generated at runtime from `devices/<model>.json` (cached under `~/.cache/open-apollo/device_maps`, with a warning), instead of falling back to the x4 map. Generated maps carry no plugin or authorization data.
- Mixer daemon: a pytest suite (`mixer-engine/tests`, no hardware needed), run in CI.
- Experimental module parameters for the sample-rate change, for testing the macOS driver's sequence (all default to the current behaviour): `rate_change=1` changes the rate with the transport stopped, waits for the firmware rate, sends the rate to every DSP and holds 1.5 s, without the reconnect or the 48 kHz pre-session; `post_start_clock=0` skips the clock write after each transport start; `ax_control_ext=0` starts the transport with AX_CONTROL 0xF instead of 0x20F.
- `devices/<model>.json` for every Apollo model (identity, capabilities, Mixer Engine route tables as channel IDs) and `tools/gen-driver-models.py`, which generates `driver/ua_models_gen.h` from them.
- `io_map` module parameter: the descriptor layout reads the firmware IO descriptor and maps each ALSA channel to its DMA slot by channel ID, as the macOS kext does. The default `io_map=-1` uses it on the Apollo x4, where it is hardware-verified, and keeps the legacy layout on every other model; `io_map=1` or `io_map=0` force one layout on every model. On the x4 the ALSA channel order and names stay the same, but S/PDIF, Virtual, MON, AUX and Talkback now carry the audio their names say (the legacy layout mislabelled every channel past MIC 4).
  - The route lists follow the TOSLink mode per direction, as the Mixer Engine does: on the x4, x8p and 8p record follows the input type and playback the output type (`Digital Output Mode`); on the Twin family both follow the input type. The input type is host-side only and set with the new `Digital Input Mode` control (default: the Mixer Engine's per-model default).
  - A layout change while streaming (firmware republish, TOSLink mode or sample-rate change) puts the open streams into XRUN so they re-prepare on the new layout. A descriptor read that is not usable keeps the last valid descriptor instead of falling back to the legacy layout.
- `/proc/asound/cardN/io_map` and `UA_IOCTL_GET_IO_MAP`: channel names, slots and the firmware IO descriptors.

### Changed
- The cold start no longer sends the captured `ua-apollo-mixer.bin` firmware stage (`mixer_fw_stage`, default off): the x4 answered every block with DSP status 0xF0010006, the macOS driver sends no firmware at start, and two cold starts without it behaved the same (ACEFACE, mixer, every rate, the DSP rings). The blob is no longer needed on the x4; `mixer_fw_stage=1` restores the stage.
- `kext_connect` is on by default: after the ACEFACE handshake every v2 Apollo gets the macOS driver's per-DSP ring connect and dated finalize, chosen by the public device type (every type a v2 Apollo gets is in the set), and the date-only disconnect at stop. The Apollo x4 never had it before; two cold starts and a warm start on titan behaved the same (ring consumed, 4/4 rates, daemon 20/20). Gen 1 x6/x8/x8p/x16 keep their ring connect at probe; an unresolved public type keeps the old serial-type rule. `kext_connect=0` restores the old choice.
- `io_map=-1` (the default) now uses the firmware IO-descriptor layout on every model, as the macOS driver does, instead of only on the x4; the x8p stays on the legacy layout its owners verified (issues #46/#52) until one of them runs `io_map=1`. On the other models the old legacy table had wrong channel and preamp counts (see apollo-linux `all-models-audit-2026-10-11.md`); `io_map=0` brings it back.
- Mixer daemon, from Codex's Console work (reconciled by behaviour, apollo-linux `codex-daemon-reconciliation-2026-10-11.md`): one input framer for text, UBJS and JSON frames; the gain companion in the client's framing, stored and pushed to other subscribers; monitor and headphone levels pushed on every step; a preamp switch writes only its own parameter; clock SETs published only when the driver accepts them (else the engine's "Unable to set value."); session /Dirty as the Mixer Engine tracks it; safe concurrent state saves; `--require-hardware`, `--preserve-hardware`, `--no-metering`.
- Mixer daemon: the device-mode word (other param 0x21) is composed as the Mixer Engine's PushDeviceMode does: TOSLink out (0x08) and in (0x10) types, ConverterMode (0x20/0x28/0x30) and the multi-unit order [7:6] (role [2:0] stays 0 for a single unit); a TOSLink input change no longer clears the output bit and the other way round. A single unit with S/PDIF still sends 0 and 8.
- Fixed: monitor Mute and MixToMono share param 0x03 (bit 1 mute, bit 0 mono) and the driver writes both bits, so setting one cleared the other; the daemon now sends both switches' states together.
- USB Apollos (untested on hardware): the init stream is built from the DSP command language (`tools/uausb`, byte-identical to the Windows capture at 48 kHz, `--rate` for other rates, `--replay` for the old path), the DSP-ready poll and code-load acks replace the fixed 2 s pause, and the mixer daemon has a USB backend (settings mailbox, readback and meters) with `--usb` or automatic selection. `install-usb.sh` installs the daemon and an access rule (`70-ua-apollo-usb-access.rules`) so it runs as the desktop user; the scan tools only read.
- Clock sources: `UA_IOCTL_GET_CLOCK_SOURCES` (ABI 1.7) returns the device's clock-source menu with the names it publishes (the kext's GetClockSourceInfo), and the daemon names `/ClockSource` entries from it as UA's Mixer Engine does (device names for the values the engine knows), so an AES/EBU or MADI unit's digital source gets its own name and value instead of being left out. The x4's list is unchanged (Internal, S/PDIF).
- The driver's reported capture delay comes from each model's converter latency (the Mixer Engine's GetInputDelay, per analog board id from readback word 33): titan's x4 is board 0, 5 frames below 100 kHz and 6 above (it reported board 2's 4.4-4.8 before); every model with data reports one, and the playback safety offset is reported on every model.
- Models: the eight Apollos the serial table cannot name (Apollo silver, 8, 16, 16 MkII, Twin, Twin MkII, Twin X, Rack) are identified by their ext_caps family and public type, the public-type family table has 22 entries (x16D on family 22), serials 2024/2025 are Twin X units and 2016/2032/2110 the Arrow/Solo, and the daemon picks its device map by public type when the device type has none.
- Driver interface: `UA_IOCTL_GET_SYSTEM_INFO` reports the firmware release word (BAR0 0x0008, x4 11.15.51635) and the device-info word (ABI 1.4); the kext's driver-parameter ids 1-5 as 0x101-0x105 (ABI 1.5); `GET_DSP_INFO` carries the kext's DSP load figures (rate overhead, DSP-measured load; ABI 1.6). The daemon judges the firmware as the Mixer Engine does and reports `/TotalDSPLoad`.
- Mixer daemon, from the Mixer Engine's model classes: converter latency and ADC delay compensation (other param 0x6a, `/openapollo/latency/*`), the monitor taper per model (48 or 54 steps), digital and virtual channel counts per rate, per-model feature flags (line reference level, PGA disable, function switch, Mon/HP switches, direct outputs, surround) with their handlers, HiZ override and knob steps, Clip/Peak hold, linked stereo inputs as one pan pair (S/PDIF R now goes hard right on its bus, as the engine writes it), Dante statuses as ints, and an empty device name refused.
- Mixer daemon: host-side preamp autogain on the Mixer Helper tree (`/auto_gain/start_auto_gain`, `stop_auto_gain`), as UA's Mixer Helper runs it on the Gen 2 models (`--autogain-any-model` for the rest).
- Mixer daemon: hardware meters on every Apollo but the MADI rack, from the Mixer Engine's generic meter layout (an input's word follows its synch-in channel).
- Per-model limits in the driver: the highest ARM preamp channel follows the mixer kind (parity/14: x6 1, x8 3, x8p 7, x16 none, ...) instead of 3 on the x4 and 7 everywhere else; HiZ impedance accepts only the model's HiZ inputs; the readback mirror follows preamps 5-8 (words 5 and 7) and reads the HP2 knob from word 7 only on models with four preamps or fewer; the headphone, talkback and Digital Output Mode controls exist only on models that have them (new `UA_MODEL_F_HP1/HP2` flags from `devices/*.json`); DMA_CTRL keeps one enable per DSP the unit has in the audio path too (the x4 runs at 0x1f instead of 0x1ff, as under macOS). The x4's control list is unchanged.
- The captured plugin-chain init is off by default (`no_plugins`, now on). After the installer put `ua-apollo-plugin-chain.bin` in `/lib/firmware`, every cold start sent the chain: the IOMMU faulted on one of its DMA references, DSP 0 stopped consuming its command ring (bus params failed with the ring full) until the Apollo was power-cycled. A cold start with the blob installed and the new default: ring consumed (1,500 bus params, 0 failed), every rate PASS. PAD/48V/Mic-Line go through the mixer settings and never needed the chain. The installer no longer installs the blob and removes an old copy, the uninstaller removes both blobs, the driver drops its `MODULE_FIRMWARE` lines, and the suspend firmware cache requests only the files an enabled stage loads.
- The DSP ready words are polled on a cold start by default (`dsp_ready_wait=1`), as the macOS driver does on the x4's capability.
- `UA_IOCTL_RING_SEND` accepts inline entries only: a DMA reference (word 0 bit 31) is refused. On titan a DMA_REF to address 0 through the old ioctl made the IOMMU fault the Apollo and wedged its transport until a power cycle. `UA_IOCTL_DSP_SRAM_DATA`/`DSP_SEND_RAW` report `-ETIMEDOUT` when the ring does not take the command (they used to return 0).
- The mixer firmware and plugin-chain blobs are checked whole before anything is sent; a malformed or incomplete plugin chain is not activated at all (it used to skip entries and report success).
- Command-buffer sends to the DSP wait up to 6 s for the ring, as the macOS driver does (ordinary commands keep their short timeout). PCM streams report 24 significant bits in their 32-bit samples. The upper interrupt bank is used on the devices the macOS driver uses it on (ext_caps bit 31, family not 6), which is every known Apollo.
- The transport starts only once FRAME_CTR has reached FRAME_CFG (`frame_ctr_gate=2`, the macOS driver's 3 reads 1 ms apart), instead of on its first non-zero value: at 176.4/192 kHz that was 4 of 0x20. On the x4 the default rate-change path stays 28/28, and the macOS driver's own rate-change sequence (`rate_change=1`) records 11 of 14 runs instead of 5. `frame_ctr_gate=0` restores the old start.
- With `period_irq=0` (the default) the driver no longer programs the period timer or enables its interrupt (vector 0x46), and no longer calls `snd_pcm_period_elapsed()` from the hard interrupt: the 1 ms hrtimer alone drives period wakeups, under the stream lock. The device now raises only end-of-buffer and notification interrupts (about 6 a second at 48 kHz).
- README: the driver builds clean on kernels 5.15 to 7.3; hardware testing is on 7.2 and Ubuntu 24.04's 6.8.
- Mixer daemon: readback pushes use the device map's monitor, headphone and preamp inputs instead of the x4's outputs 18-20 and inputs 0-3. A preamp GainC of 0 reads as 0 dB (was 10 dB) and preamp 2's gain field is 6 bits, as in the Mixer Engine.
- Mixer daemon: the router reads each model's monitor, headphone and CUE outputs and its preamp inputs (up to 8) from the device map, and derives input buses for analog 1-8, Dante/MADI/analog 9-16 and AES/EBU; it was hard-wired to the x4 (on the x8p the monitor is output 22).
- Mixer params the macOS driver rejects for the device's mixer kind return `-EINVAL` (on the x4: other params 0x2a-0x2d, 0x33-0x37, 0x42, 0x49, 0x83-0x86 and input param 0x15), as do ids above 0x8a. Input params 0x13 (route) and 0x16, and phase on inputs past the preamps, go to the DSP as ring commands as the macOS driver sends them, instead of overwriting mixer settings 26/29/34/37. A bus enable is sent only when it changes the bus's state (the first request per bus after probe always goes out).
- DSP block responses are decoded into the macOS driver's result codes and logged by name; block and firmware sends wait up to 5 s and 150 s, as the macOS driver does, and end as soon as the DSP answers. `UA_IOCTL_LOAD_FW_DSP` is retired (`-ENOTTY`): the macOS driver loads DSP 0 only and the other DSPs boot themselves.
- Probe fails with `-ENODEV` when FPGA_REV or ext_caps reads 0xFFFFFFFF (device gone) or ext_caps reports more than 8 DSPs.
- The transport starts with AX_CONTROL 0xF, as the macOS driver does for a unit on its own clock, instead of 0x20F (`ax_control_ext=1` restores it). Both passed every rate change on the x4; 0x20F is the peer-clocked (multi-unit) value.
- Kernel log: per-stream, per-start and per-rate-change register dumps, IO descriptor slot lists and the DSP service ticks are debug-level (dynamic debug brings them back); a missing optional plugin-chain blob is reported once. A run of 14 duplex rate changes logs about 25 lines.
- UCM2: the `HiFi` profile matches the Apollo x4 only (it describes the x4's layout) and documents the v2 channel layout; its devices are named `Outputs` and `Inputs`.
- Device-type names follow the kext (`0x20` x6, `0x21` x8, `0x22` x8p, `0x23` x16, `0x35` x16D, `0x37`–`0x3a` Gen 2 rack units); serial prefixes 2107–2110 added. The x8p resolves by serial (device type `0x22`); PCI subsystem `0x0014` is only a fallback.
- The legacy layout (`io_map=0`, and the default on every model except the x4) is unchanged: every device type keeps its DMA channel counts and its preamp/HiZ controls, and the x8p keeps 34/32 and 8 preamps under its corrected type `0x22`. Device types the old model table did not list (`0x3B`, `0x3C`, `0x3E`–`0x41`: serials 2090, 2091, 2107–2110) take their preamp counts from the generated model data. With the descriptor layout, all preamp/HiZ counts come from the model data and the channel counts from the firmware (the x4 keeps its 4 preamps and 2 HiZ inputs).
- The cold start no longer uploads the captured DSP "programs" (command `0x00360000`): the kext never sends it, and on the x4 it timed out with `DSP program load failed: -110` on every cold start.
- `/dev/ua_apolloN` is no longer world-writable: the new `70-ua-apollo-access.rules` gives it to the logged-in desktop user (uaccess) and the `audio` group, and the raw register, DMA, DSP-ring and firmware ioctls need `CAP_SYS_RAWIO`. The ioctls the mixer daemon uses are unchanged. The raw ARM CLI ioctl is refused (`-ENOSYS`), as the driver's own CLI path already was, since CLI commands freeze the ARM MCU.
- Documentation moved to the [GitHub wiki](https://github.com/rolotrealanis98/open-apollo/wiki). The `docs/` directory and the open-apollo-docs site are retired; old `open-apollo-docs.pages.dev` links redirect to the wiki.

### Fixed
- Analog inputs stayed silent after the switch from Windows/macOS: with `kext_connect` (default since this release) the driver sent every DSP the per-DSP ring connect even when it found the mixer DSP running, and that makes the DSPs drop the Console input strips the other OS built. Linux cannot build them yet, so the mic recorded digital zero. A DSP found running at probe (`dsp_inherited`) now keeps its state: no ring connect for that device. titan: strips built by macOS Console, Apollo moved to titan powered: input 1 recorded at -60 dBFS (was digital zero), also after a driver reload. A resume that has to cold-start the DSP (the Apollo lost power) clears the flag, so the fresh DSPs are connected again.
- Leaving 176.4/192 kHz less than about 3 s after the clock got there wedged the x4's firmware rate: it stayed at 192 kHz and every other rate recorded silence until a reload or an Apollo power cycle (found by the F3 soak on titan; 3 of 4 runs with a 2 s 192 kHz stream). The clock now stays at a Hi-band rate for `hi_dwell_ms` (3000) before any change; titan: 52 back-to-back rate changes incl. 1 s Hi-band streams, the firmware followed every one, ratecheck 4/4.
- Mixer daemon: buffer size, sample rate, transport, DSP load and latency are polled once a second even with no client connected, so a Console that connects sees the running stream's `/BufferSize` instead of the start-up 256 (titan: period 2048 while the daemon still said 256).
- Mixer daemon (review before the first hardware run): a clock SET to the rate or source in effect no longer pauses and rewrites the clock; init keeps monitor mono when the monitor is also muted; a UBJSON count or length past the frame's bytes is rejected (a 9-byte frame could spin the event loop); commands before an unframeable header in the same read are still answered; device-mode bit 0x10 goes out only with the driver's `toslink_in_bit` (the x8p sends 0x08 as before); a saved TOSLink, ConverterMode or MultiUnitOrder is re-applied on start.
- USB backend: a bad first readback retries instead of resetting the unit to the defaults, a failed settings flush keeps its change for the retry, init skips the kind-gated and x4-default monitor params (the mixer kind is unknown), and a missing libusb counts as no USB device instead of crashing.
- DSP command rings work after an Apollo power cycle: ring init wrote all eight DMA reset strobes along with the enables (DMA_CTRL 0x1ffff, issue #46's readback, now seen on the x4), the DSP never consumed its command ring, and faders, pans and sends did not reach the DSP until the unit had been initialised by another OS. One enable bit per DSP is now written and no strobe is left set (`dma_per_dsp`, default on).
- Teardown: the DSP service stop always waits for a running pass, the service and the period timer cannot be restarted on a removed device, and a failed probe quiesces the hardware and turns off bus mastering before freeing its DMA buffers (from the parallel Codex work).
- The Dante clock source (0x09) is accepted on devices that offer it.
- `ua_dsp_configure_modules` uses 256-byte module slots: with 128 the next header overwrote the last six words of module 0's I/O descriptor (found by the parallel Codex work; the function has no caller).
- PipeWire duplex starts no longer begin with a burst of playback xruns: a stream now starts at the shared transport's live position (`pcm_live_start`, default on; prepare sets the ALSA hardware pointer to SAMPLE_POS, as the RME Hammerfall drivers do), instead of at 0 on a transport already running. On the x4 a duplex start went from 7 playback xruns to 1.
- The notification status (0xC030) is cleared only after every bit of the pass has been acted on, as the macOS driver does.
- `period_irq=1` at 48 kHz: the timer vector is re-armed from the IRQ thread after the period is served (it used to re-arm in the hard IRQ and let a second interrupt for the same boundary through), TIMER_CFG is written on every transport prepare, and after a rate change the timer's transport is restarted once the clock has locked at the new rate (`period_irq_settle`, default on): a timer started on the still-unlocked clock after 192 to 48 kHz ran about 13% fast. On titan every timer run of the matrix is now exact (phase 3 frames); `period_irq_trace` records the timer cadence for diagnosis.
- The driver's ALSA sync skips a hardware readback the Mixer Engine would skip (word 38 or 39 reading 0xFFFFFFFF).
- Mixer daemon: a readback snapshot whose check word (38 or 39) is all ones is dropped, as the Mixer Engine drops it, instead of being decoded; at start the daemon waits for the next snapshot instead of falling back to the defaults.
- Mixer bus params write both the left and the right coefficient entry (the side is in the DSP command, as the macOS driver sends it); the daemon writes both for fader, pan, mute and solo. Pan and stereo coefficients used to change only the left half.
- CUE 1/2 mono, and other params 0x0a, 0x0f, 0x23 and 0x25, use the macOS driver's bit order; CUE mono used to set the bit the macOS driver uses for mute. Input params 0x07, 0x08, 0x10, 0x11 (HiZ impedance), 0x12, 0x14 and 0x17 write the setting, lane and width the macOS driver uses, and stereo Link writes both pair bits from the leader channel only. The identify param keeps to its 3-bit field.
- The connect-finalize date counts days from 2007-01-01 UTC, as the macOS and Windows drivers do, not from 1970.
- v1 firmware takes its DSP count from FPGA_REV[31:28], as the macOS driver does, not from the PCI subsystem id. The DSP check at probe reads each DSP's status window instead of an unrelated ring register.
- Model data: HiZ on input 1 of the Twin family, Arrow and Solo; the Twin X talkback input; four CUE buses on the original Apollo; the Realtime Rack's digital I/O is MADI.
- Reboot, power-off and suspend now stop the Apollo first (`.shutdown` and suspend/resume): mute, transport off, DMA quiesced, disconnect signal. Unloading the module no longer leaves the audio extension connected, so `rmmod` + `insmod` reconnects and keeps the mixer DSP running.
- Preamp PAD, 48V and Mic/Line work from Linux. Mixer settings are now written as the macOS driver writes them, each change once and then cleared (`mixer_mailbox`, default on), instead of re-sending every touched field on every update; with the old method the DSP ignored PAD, 48V and Mic/Line. The front-panel buttons and the monitor knob also keep their changes instead of being overwritten by the next settings update. `mixer_mailbox=0` restores the old behaviour.
- The DSP command ring is circular: mixer commands no longer stop for good after about 1,000 changes.
- ASPM L0s is turned off on the Apollo's PCIe link; with it on, the link logged a steady stream of correctable errors while streaming.
- Recording works after every sample-rate change on the x4: a 192 kHz stream started while the clock was already at 176.4 or 192 kHz used to record nothing, and a 176.4 kHz one did about 1 time in 6.
- Unplugging, powering off or unbinding the Apollo while the mixer daemon, PipeWire or another program has it open no longer leaves the driver using freed memory: the device structure lives until the last `/dev/ua_apolloN` file is closed, ioctls in flight finish before the teardown and later ones get `-ENODEV`, and the ALSA card is freed only after its open files are closed.
- Recording and playback at the same time: a stream that stops (a short `aplay` ending) no longer stops the other one's period wakeups, which used to make it fail with an I/O error after 10 s. Streams that lose the transport (AER, a stopped transport) are put into XRUN instead of stalling.
- A preamp switch or gain set through the ioctl while the mixer is not ready (during a resume re-init) now returns an error instead of reporting success and updating the ALSA control.
- After a DSP command that got no response, the next commands on that DSP no longer time out: the leftover response slot is dropped first.
- PCIe error recovery (AER) reconnects the Apollo the way system resume does; before, it reset every DMA engine (killing the mixer DSP) and in practice never recovered.
- Firmware blob parsing checks every offset and length for overflow, and the plugin chain never asks the device to read past a payload buffer.
- `UA_IOCTL_DMA_TEST` refuses to run while a stream is open and always stops the transport it started.
- The driver builds with clang: the GCC-only optimisation overrides are skipped there.
- Mixer daemon: talkback works from a client. The device maps keep `TalkbackOn` at the tree root (`/TalkbackOn`), and the daemon only routed `/devices/0/TalkbackOn` to the hardware; the talkback button's state is now also reported on `/TalkbackOn`.
- Mixer daemon: a front-panel monitor-knob change now updates `CRMonitorLevel` (dB) as well as `CRMonitorLevelTapered`, so clients reading the dB value no longer see a stale level.
- Mixer daemon: `/ClockLocked` follows the hardware's clock-lock flag (readback word 6 bit 31, valid with bit 30) instead of always reading locked.
- ALSA preamp controls (gain, 48V, PAD, phase, low cut, Mic/Line) write the hardware; they used to change only the driver's cached value. Gain uses the macOS triplet and the 10–65 dB range.
- Monitor mute and mono no longer clear each other (both go through the same parameter).
- ALSA control change events carry the control's numid, so alsa-lib clients see them; enum controls never report a value outside their list.
- Mixer daemon: a client SET of the monitor level in dB (or tapered) updates the other value too, so a later knob change to the same position is still reported.
- Mixer daemon: `?recursive=0` is not recursive.
- Model data: duplicate and leaked mixer input names in five `devices/*.json` files, and missing subsystem IDs for the 8p and Solo.
- Mixer daemon: send meters (AUX 1/2, CUE 1-4) and post-fader input metering (`/PostFaderMetering`) are computed from the input meters as the Mixer Engine does: input level plus the send gain, plus the fader for a post-fader send (the send's override, else the AUX bus's or HP n's SendPostFader); muted or bypassed paths read silent. Send meters used to show the raw input level.
- Mixer daemon: on the Apollo x4 the meters now come from the hardware, as on macOS: the DSP writes every input's level (Virtual included) and the monitor and AUX bus levels into readback words 8-25, which the daemon used to treat as unused. The PipeWire/ALSA capture meters stay as the fallback for other models.
- Mixer daemon: HiZ jack detection is reported per input (readback word 0 bit 24 = input 1, bit 25 = input 2; only bit 24 was decoded), and the init sequence enables the CUE bus routing paths 5 and 6 instead of disabling them (the driver takes the parameter ID as the enable value).
- Mixer daemon: level meters work while PipeWire is running. They used to need the ALSA capture device to themselves (and pyalsaaudio), so every meter read silence on a desktop; they now come from the Apollo's PipeWire capture node, falling back to direct ALSA capture without PipeWire. Each meter reads the channel it names (input meters used to read the record channel with the same index, so ADAT 1 showed S/PDIF L and so on), the monitor and AUX bus meters work, and peak hold holds while the level stays at the peak.
- Clock Source: the control, `UA_IOCTL_SET_DRIVER_PARAM` (param 1) and the mixer daemon use the device's source values (Internal 0x0C, S/PDIF 0x00, ADAT 0x05, Word Clock 0x07) instead of the index 0–3. The control read 12, a value outside its list (so `alsactl` could not restore it), and choosing Internal selected S/PDIF. Sources the device doesn't offer (it lists them at connect; the x4 has no Word Clock) are refused, and the source is committed only once the device acknowledges it.
- Playback and capture can no longer run at different rates; they share one clock. Once one direction has a rate, the other is offered only that rate, and the Sample Rate control and `UA_IOCTL_SET_DRIVER_PARAM` (param 0) return -EBUSY for another rate while a stream is open. Before, the two re-prepared each other's rate in a loop, and the DSP could end up recording silence until a power cycle.
- Mixer daemon: a Console sample-rate change works while PipeWire holds the Apollo. The daemon sets PipeWire's `clock.force-rate` (cleared again when the rate goes back to PipeWire's default) instead of changing the clock under PipeWire's streams, which PipeWire undid at its next prepare; `/SampleRate` now follows the driver's rate. `clock.force-rate` is global, so PipeWire's other devices follow too.
- WirePlumber rules: the Apollo nodes allow every rate (`audio.allowed-rates`) instead of pinning `audio.rate = 48000`, which kept the Apollo at 48 kHz, and both nodes are in one `node.group`. Playback and capture share one clock; without the group a forced rate moved only the playback node, and the two re-prepared at different rates in a loop, about 5 changes a second, which left the DSP recording silence until the Apollo was power-cycled.
- Mixer daemon: starting it no longer resets the Apollo. Preamp gain and switches, link, and the monitor level, mute, mono and dim are taken from the hardware, so front-panel changes made while no daemon ran are kept; safe defaults (monitor at minimum) are only used when there is no hardware readback. Input faders and mutes a client set are restored from the saved state instead of every input being muted, and the init sequence is sent once instead of twice when a client connects during startup.
- Mixer daemon: after the front-panel gain knob moves, setting a preamp's gain back to the value a client last set now reaches the hardware; the daemon used to drop it as a duplicate.

## [1.0.0] - 2026-03-22

### Added
- Linux PCIe kernel module for Apollo Thunderbolt interfaces
- Full duplex audio: 24-channel playback + 22-channel capture (4 analog inputs and 6 analog outputs verified; S/PDIF, ADAT, and virtual channels unverified)
- All 6 sample rates (44.1kHz – 192kHz)
- Preamp control via ALSA mixer: 48V phantom, pad, gain, phase, low cut
- 50 ALSA mixer controls
- PipeWire integration with named virtual I/O devices (Mic 1–4, Monitor L/R, Line Out)
- Dynamic PCI address discovery (`apollo-setup-io`)
- One-command installer with DKMS support
- WirePlumber rules (disable-mmap, no suspend, S32LE/48kHz)
- UCM2 ALSA profile
- udev auto-detection and profile setup
- Systemd user service for virtual I/O auto-setup
- System tray indicator
- Anonymous install telemetry (opt-in)
- Documentation site at open-apollo-docs.pages.dev

### Fixed
- PipeWire loopback module wiring (capture/playback sides were swapped)
- PCIe ASPM/bridge setup moved out of real-time audio thread
- Clock write ordering (after transport start, not before)

### Known Issues
- Virtual I/O devices may not auto-appear on boot (run `apollo-setup-io` manually)
- `alsactl restore` can freeze the DSP — remove Apollo entries from asound.state
- Only tested on Apollo x4 — other models need community testing
